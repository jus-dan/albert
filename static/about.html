Wie funktioniert die Wunschmaschine?

Technischer Überblick über die Architektur: welche Komponente läuft lokal, welche externen APIs werden angesprochen, und welche Daten fliessen wohin.

Lokale Komponente

Ein Python/FastAPI-Backend läuft auf diesem Rechner. Es hält eine WebSocket-Verbindung zum Browser (Audio-Capture über die Web Audio API) und eine zweite WebSocket-Verbindung zur OpenAI Realtime API. Es reicht den Audio-Stream in beide Richtungen durch, wertet Function-Call-Events aus (submit_wish, submit_challenge, confirm_print, end_conversation) und spricht bei einem Druckauftrag direkt den Windows-Druckertreiber per GDI (win32print) an -- kein Zwischenschritt über eine PDF-Anwendung.

Wird meine Stimme wirklich übertragen?

Ja. Es läuft keine lokale Spracherkennung (kein Whisper- oder sonstiges STT-Modell auf diesem Rechner). Der Audio-Stream (PCM16, 24 kHz) wird per WebSocket direkt an wss://api.openai.com/v1/realtime übertragen, Modell gpt-realtime -- ein Speech-to-Speech-Modell, das Spracherkennung, Sprachverständnis/Antwortgenerierung und Sprachsynthese in einem einzigen Modellaufruf kombiniert, ohne Umweg über eine separate Text-Transkription. Es gelten OpenAIs Nutzungsbedingungen für API-Traffic (nicht identisch mit den Regeln für ChatGPT im Browser).

Airtable REST API

Ein per Function Call (submit_wish / submit_challenge) erfasster Eintrag wird per POST-Request über die Airtable REST API in die Tabelle _input_pipeline der Base "HSG-SSI-ecosystem (DEV_v2)" geschrieben. Das Team sichtet und triagiert die Einträge dort (Feld triage_status). Ein Name ist kein Pflichtfeld, nur wenn er freiwillig genannt wird.

Was wird NICHT gemacht?

Keine Kamera, keine Videoaufnahme, keine lokale Aufzeichnung oder Zwischenspeicherung des Audio-Streams. Es gibt keinen Session-Speicher zwischen zwei Gesprächen (kein Cookie, kein Verlauf) -- nach der Verabschiedung wird die WebSocket-Verbindung geschlossen und die Oberfläche zurückgesetzt.
